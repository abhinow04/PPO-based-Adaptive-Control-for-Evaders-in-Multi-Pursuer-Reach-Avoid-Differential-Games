# PPO-based-Adaptive-Control-for-Evaders-in-Multi-Pursuer-Reach-Avoid-Differential-Games

A multi-agent pursuit-evasion simulation combining **classical differential game theory** (Apollonius circle barrier analysis, Isaacs' pursuit-evasion framework) with a **PPO-trained reinforcement learning controller**, enabling an evader to adopt adaptive, learned evasion strategies in scenarios where classical theory predicts inevitable capture.

This project builds on prior work formalizing the *n*-pursuer, *m*-evader reach-avoid differential game via linear-programming-based role assignment ([Agasti, Reddy & Bhikkaji, 2023](https://arxiv.org/abs/2303.07885)), extending it with a learned evader policy for the pursuer-favourable barrier region.

---

## Overview

Two pursuers attempt to intercept a single evader before it reaches a stationary target. The classical differential game solution partitions the state space into a **pursuer-winning region** (`B > 0`) and an **evader-winning region** (`B ≤ 0`), where `B` is the barrier function computed from each pair's relative position and speed ratio. Classical closed-form control laws are optimal in each region — but only if both players execute them perfectly, which real deployed pursuers rarely do.

This project replaces the evader's behaviour with a **PPO (Proximal Policy Optimization)** policy, allowing it to learn adaptive evasive manoeuvres — turning, looping, timing crossings — that exploit the gap between theoretical optimality and practical pursuer implementations.

## Key Features

- **Hybrid control**: classical closed-form strategy where it's provably correct, PPO-learned strategy where classical theory offers no useful guidance
- **Compact 1D action space**: a single *deroute multiplier* `m ∈ [-1, 1]` rotates the evader's heading by up to ±160° off the direct line to target, rather than a raw 2D velocity vector
- **Curriculum learning**: pursuer speed and safe-margin difficulty ramp progressively across training
- **Linear-programming assignment**: optimal pursuer-to-evader matching via `scipy.optimize.linprog`, following the LP formulation in the base thesis
- **Full training and post-game analytics**: reward/win-rate/loss curves, deroute multiplier evolution, agent speed and angular velocity profiles, batch win-rate scatter
- **Physical robot deployment path**: ROS2 + MQTT bridge for LEGO EV3 holonomic robots, tracked via OptiTrack motion capture (see `ev3_*.py`, not required for simulation-only use)

## Quick Start

### Run a simulation

```bash
python3 main.py
```

This randomly places 2 pursuers and 1 evader, runs the linear-programming assignment, and opens a live matplotlib window showing the trajectory as the game unfolds. On completion, additional figures are shown automatically:

- Distance to Pursuer 1 / Pursuer 2 / Target over time
- Evolution of the deroute multiplier `m`
- Pursuer and evader speed over time
- Angular velocity of all agents

### Train the PPO evader from scratch

```bash
python3 ppo.py --episodes 2000
```

Produces `ppo_evader.pth` and `training_curves.png` (episode reward, win rate, capture rate, training loss — all vs. episode number).

Key CLI options:

```bash
python3 ppo.py \
  --episodes 2000 \
  --pursuer-speed-start 20 --pursuer-speed-end 30 \
  --entropy-coef 0.05 \
  --warmup-episodes 400
```

### Run many trials and get an aggregate win rate

Since a single game only produces a binary win/loss outcome, use the batch runner for a statistically meaningful win rate:

```bash
python3 -c "import assign; assign.run_batch_trials(num_trials=100)"
```

### Diagnose a trained checkpoint

```bash
python3 diagnose_checkpoint.py ppo_evader.pth
```

Checks whether the deroute multiplier is genuinely state-responsive (rather than collapsed to a near-constant value — a failure mode encountered during development), and reports a fresh out-of-sample win rate.

## Method Summary

### State representation

```
S_t = [x_e, y_e, x_p1, y_p1, x_p2, y_p2, x_t, y_t]
```

The evader's position, both pursuers' positions, and the target — identical information to what the classical controller has access to, with no privileged state.

### Action: the deroute multiplier

Instead of a raw velocity vector, the evader's policy outputs a single scalar `m ∈ [-1, 1]`:

```python
heading = angle_to_target + m * MAX_DETOUR_ANGLE_RAD   # MAX_DETOUR_ANGLE_RAD = 160°
velocity = [cos(heading), sin(heading)] * evader_speed
```

`m = 0` is the direct line to target; `m = ±1` allows up to a 160° detour, sufficient for genuine looping manoeuvres around a threatening pursuer.

### Network architecture

Shared-torso actor-critic, ~4,900 parameters total:

```
Input (8) → Linear(8→64) + Tanh → Linear(64→64) + Tanh
                                  ├── Actor head:  Linear(64→1) → tanh → mean of Gaussian(m)
                                  └── Critic head: Linear(64→1) → V(s)
```

### Reward

```
R_t = w_target · Δd_target
    + w_safety_eff · Δd_pursuer
    - step_penalty
    + w_turn_bonus · danger · |m|
    (+ terminal bonus/penalty on reach/capture)
```

`w_safety_eff` scales up sharply as the pursuer closes in; `w_turn_bonus` directly rewards decisive turning under threat, added after empirical testing showed the indirect distance-based safety term alone wasn't sufficient to teach responsive evasion.

### Training

PPO with clipped surrogate objective, GAE (`λ=0.95`, `γ=0.99`), curriculum-annealed pursuer speed (20→30) and danger radius (150→80) across the first several hundred episodes.

## Results

- Fresh out-of-curriculum evaluation: **~85–94% win rate**, depending on pursuer behaviour model (see `pursuer.py` notes below)
- Full `evader.py` → `pursuer.py` pipeline (not just the isolated training environment) validated independently
- Diagnostic checks confirm the deroute multiplier responds meaningfully to threat proximity rather than collapsing to a constant output

## Pursuer Behaviour Models

Two pursuer models were implemented and compared during development — set at the top of `pursuer.py`:

1. **Continuously adaptive**: recomputes the optimal Apollonius-circle intercept heading every timestep from live positions (the textbook game-theoretic optimal strategy).
2. **Locked straight-line**: computes its heading once, at the start of the episode (per Lemma 1 of Agasti et al. — since the game's terminal payoff makes the costate constant under optimal play, the truly optimal heading is itself constant), then holds it for the rest of the episode.

The locked model produces a fully predictable adversary and was used for the primary evaluation; the adaptive model is closer to a "worst case" reactive pursuer and yields lower win rates, since it can re-target the evader's actual position rather than a stale interception point.

## Known Limitations

- The action-space rotation direction (`m`'s sign convention) is learned implicitly from reward, not derived from an explicit "which side is the pursuer on" signal — this can occasionally produce turns that curve toward rather than away from a threat in edge cases; see open issue below.
- `log(σ)` (policy exploration noise) is a single learnable scalar shared across all states rather than state-conditioned, so exploration breadth doesn't adapt to how uncertain the policy currently is.
- Classical barrier-region formulas assume `α = v_evader / v_pursuer < 1` (pursuer strictly faster); the code will divide by zero if this is violated, including transiently during curriculum warmup if misconfigured.

## Open Issues / Future Work

- [ ] Give the network an explicit relative-position or "away-from-pursuer" signal in the observation, rather than relying entirely on learned geometry from raw coordinates
- [ ] State-conditioned exploration noise (a learned `log(σ)` head rather than a free scalar)
- [ ] Extend beyond the 2-pursuer/1-evader case to general *n*-pursuer/*m*-evader assignment with the learned evader
- [ ] Obstacle-aware training (current arena is open, matching the physical OptiTrack testing environment)
- [ ] Physical hardware validation of the PPO-trained policy on the LEGO EV3 platform (currently validated only for the classical controller)

## Physical Deployment (Optional)

The `ev3_*.py` / `gogoal.py` / `initialise_game.py` files (not required for pure simulation) support deployment to 3 LEGO EV3 holonomic robots tracked via an OptiTrack motion capture system:

- **`ev3_mocap.py`** — publishes OptiTrack pose data (via VRPN) to ROS2 topics
- **`initialise.py`** — subscribes to pose topics, provides positions to the game logic
- **`ev3_bridge.py` / `ev3_sub.py`** — ROS2 ↔ MQTT bridge for sending wheel velocity commands to the physical robots
- **`gogoal.py`** — inverse/forward kinematics for the 3-wheel omnidirectional drive

See the base thesis (Section 3.4, Section 4.1) for full physical setup details and calibration notes.
